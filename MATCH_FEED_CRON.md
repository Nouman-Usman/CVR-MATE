# Registering the Daily Match Feed QStash schedule

The Daily Match Feed is generated by a cron endpoint that must be triggered **once every hour**.
There is no `schedules.create` call in the codebase (schedules are provisioned out-of-band, like the
other crons), so you register the schedule **once** against QStash. This guide gives three ways to do
it — pick one.

---

## What you are registering

| Field | Value |
|---|---|
| **Method** | `POST` |
| **Destination** | `https://cvr-mate-hfdc.vercel.app/api/cron/match-feed` |
| **Cron** | `0 * * * *`  (top of every hour, **UTC**) |
| **Body** | empty (`{}`) — the route reads no input |

> The destination shown is your production deployment (`https://cvr-mate-hfdc.vercel.app`). If you serve
> the app on a custom domain (e.g. `https://cvr-mate.dk`), use that instead — just make sure it's the
> deployment that has the env vars below. **Do not** use `localhost` — QStash must reach it over the
> public internet.

**Why hourly?** The route computes the current hour in **Europe/Copenhagen** and only processes users
whose `userBrand.emailNotificationHour` equals that hour. So one plain hourly UTC schedule delivers each
user their feed at *their* configured local hour, and DST is handled inside the app — not in the cron
expression.

---

## Authentication (read this first)

The route (`app/api/cron/match-feed/route.ts`) authorizes a request if **either**:

1. **QStash signature** is valid — verified with `QSTASH_CURRENT_SIGNING_KEY` + `QSTASH_NEXT_SIGNING_KEY`.
   QStash signs every request it sends, so a QStash-created schedule passes automatically. **This is the
   recommended path** and needs no custom header.
2. **`Authorization: Bearer <CRON_SECRET>`** matches — used for manual `curl` testing, and as a fallback
   if you don't run the signature keys.

### Required environment variables

Set these in your **production** environment (e.g. Vercel → Project → Settings → Environment Variables):

| Variable | Needed for | Notes |
|---|---|---|
| `QSTASH_TOKEN` | creating the schedule | From console.upstash.com → QStash → **Details**. Already used by `lib/email/queue.ts`. |
| `QSTASH_CURRENT_SIGNING_KEY` | the route to trust QStash | From the same QStash page → **Signing keys**. |
| `QSTASH_NEXT_SIGNING_KEY` | key rotation | Same page. |
| `CRON_SECRET` | manual `curl` testing (optional) | Any long random string. `openssl rand -hex 16`. |

After changing production env vars, **redeploy** so the running app picks them up.

## Method A — Upstash Console (no code)

1. Go to **https://console.upstash.com** → **QStash** → **Schedules** tab.
2. Click **Create Schedule**.
3. Fill in:
   - **Destination (URL)**: `https://cvr-mate-hfdc.vercel.app/api/cron/match-feed`
   - **Method**: `POST`
   - **Schedule (cron)**: `0 * * * *`
   - **Body**: `{}`  (optional; can be left empty)
   - **Retries**: `3` (optional)
   - *(Optional fallback auth)* under **Forward Headers**, add
     `Authorization` = `Bearer <your CRON_SECRET>` — only needed if you are **not** relying on the
     signature keys.
4. Click **Schedule**. You'll get a schedule id like `scd_xxx`. Done.

## Method B — REST API (one `curl`)

QStash's schedule endpoint is `POST /v2/schedules/{destination}` with the cron in the `Upstash-Cron`
header. Set `QSTASH_TOKEN` in your shell first (`export QSTASH_TOKEN="..."`), then:

```bash
curl -X POST \
  "https://qstash.upstash.io/v2/schedules/https://cvr-mate-hfdc.vercel.app/api/cron/match-feed" \
  -H "Authorization: Bearer $QSTASH_TOKEN" \
  -H "Upstash-Cron: 0 * * * *" \
  -H "Upstash-Method: POST" \
  -H "Content-Type: application/json" \
  -d '{}'
```

Response: `{"scheduleId":"scd_xxx"}`.

*Fallback auth (only if you are NOT using the signature keys):* add
`-H "Upstash-Forward-Authorization: Bearer <YOUR_CRON_SECRET>"`. QStash forwards any `Upstash-Forward-*`
header to your endpoint (stripping the prefix), so this arrives as `Authorization: Bearer <CRON_SECRET>`.

## Method C — SDK script (uses your existing `@upstash/qstash`)

A ready-to-run script lives at `scripts/register-match-feed-schedule.ts`. Edit the destination (or set
`MATCH_FEED_CRON_URL`), make sure `QSTASH_TOKEN` is in your environment, then run:

```bash
# load your env (or export QSTASH_TOKEN + MATCH_FEED_CRON_URL manually)
export QSTASH_TOKEN="..."
export MATCH_FEED_CRON_URL="https://cvr-mate-hfdc.vercel.app/api/cron/match-feed"

pnpm exec tsx scripts/register-match-feed-schedule.ts
```

It lists existing schedules first and **skips** if one already targets the destination, so running it
twice will not create a duplicate.

## Verify it works

**1. Confirm the schedule exists** (Console → QStash → Schedules), or via API:

```bash
curl -s "https://qstash.upstash.io/v2/schedules" -H "Authorization: Bearer $QSTASH_TOKEN" | jq
```

Look for `"cron":"0 * * * *"` pointing at `/api/cron/match-feed`, and a future `nextScheduleTime`.

**2. Trigger the endpoint manually** (does not wait for the hour). Requires `CRON_SECRET` set in prod:

```bash
curl -i -X POST "https://cvr-mate-hfdc.vercel.app/api/cron/match-feed" \
  -H "Authorization: Bearer <YOUR_CRON_SECRET>"
```

Expect `200` with `{"ok":true,"currentHour":<0-23>,"counts":{...}}`. If `counts.processed` is 0, that's
usually correct — it only processes users whose `emailNotificationHour` equals the current Copenhagen hour.

**3. Check the QStash message log** (Console → QStash → **Logs**) after the next top-of-hour to confirm a
`200` delivery.

## Managing the schedule

```bash
# List (grab the scheduleId)
curl -s "https://qstash.upstash.io/v2/schedules" -H "Authorization: Bearer $QSTASH_TOKEN" | jq

# Pause / Resume
curl -X PATCH "https://qstash.upstash.io/v2/schedules/<scheduleId>/pause"  -H "Authorization: Bearer $QSTASH_TOKEN"
curl -X PATCH "https://qstash.upstash.io/v2/schedules/<scheduleId>/resume" -H "Authorization: Bearer $QSTASH_TOKEN"

# Delete
curl -X DELETE "https://qstash.upstash.io/v2/schedules/<scheduleId>" -H "Authorization: Bearer $QSTASH_TOKEN"
```

To **update**, delete and re-create, or in Method C pass the existing `scheduleId` to `.create()`.

## Troubleshooting

| Symptom | Cause / fix |
|---|---|
| `401 Unauthorized` on delivery | Signing keys not set (or not redeployed). Set `QSTASH_CURRENT_SIGNING_KEY` + `QSTASH_NEXT_SIGNING_KEY` in prod and redeploy, **or** add the `Upstash-Forward-Authorization: Bearer <CRON_SECRET>` header to the schedule. |
| `200` but `counts.processed: 0` every hour | Usually fine (no users due this hour). If it's *always* 0: confirm users have a `userBrand` with `emailNotificationHour` set, and are on Professional/Enterprise (the feed is gated). |
| `500` / DB errors | Migration `0030` not applied. Run `pnpm db:migrate` (needs working `DATABASE_URL`). The tables `match_feed_item` + `match_profile` must exist. |
| No matches ever generated | Check the user has a completed Knowledge Base (`userBrand` + `aiEnrichment`); cold-start with no brand returns an empty feed by design. |
| Duplicate schedules | Delete extras; Method C skips creation when one already targets the destination. |

**Cost sanity check:** each run makes **one** Haiku call per due user (only for users not already
generated today). To watch spend, tail your app logs for the `match-feed` route and confirm one LLM call
per user per day.
